Self-hosted control room for coding agents

Agents do the work. You make the decisions.

Switchyard runs coding agents through playbooks kept in your repository. At each gate the run stops and shows you two things separately: what the engine verified itself, and what an agent only claimed.

It starts in simulate mode, with scripted agents and dry-run commands, so you can watch a run end to end before you point it at a real repository.

01The problem

A person still carries every thread an agent starts.

A coding agent can turn an error report into a pull request. Someone still starts the session, hands over the context, waits, and reads the summary at the end.

  1. Shepherd every thread

    You start each session, give it the context, check on it and pass its result to the next one, and you do that for every task at once.

  2. Re-read every claim

    A summary that says the tests pass is still only a sentence, so you run the tests again yourself before you trust it.

  3. Decide when it is safe to merge

    The decision reaches you with no line drawn between what was checked and what an agent only said.

02How it works

A signal starts a playbook, and the playbook stops at a gate.

When something happens in your tools, a watch matches the signal to a playbook, and the playbook runs until a person has to decide.

    • Sentry issue
    • Failed check on the default branch
    • New pull request
    • Schedule
    • Signal sent by hand

    1Signal

    A signal can be a Sentry issue, a failed check on the default branch, a newly opened pull request, a schedule, or one you send by hand. Webhooks are checked against the provider’s HMAC signature before anything runs.

  2. red-main error-to-fix review-pull-request

    2Watch

    A watch matches the signal to a playbook. In this picture a Sentry issue is switched onto error-to-fix.

  3. 3Playbook

    In an agent step, a named operator works in a coding session through the Claude Code or Codex command line on your machine. In a command step, the engine runs the command itself and records the exit code.

  4. approve reject

    4Gate

    The run stops until a person answers. If they approve, the run continues, and if they reject, this playbook stops the run.

03Evidence

Every line of evidence says where it came from.

A gate sorts what the run produced into two groups. An agent’s claim may well be right, but nobody has checked it yet, and its label says so.

Verified by the engine

The engine did the work itself and recorded what happened.

  • npm testThe engine ran the command itself, as a command step.
  • exit 0This is the exit code the engine saw, and the playbook expected 0.

Claimed by an agent

An agent wrote it in its report, and the engine did not check it.

  • @fitter“The regression test fails without the fix.”
  • @checker“No findings in the diff.”

In simulate mode a third label appears: simulated. It marks output from a scripted run, which proves nothing about your code.

04Playbooks

A playbook is a JSON file in your repository.

It is reviewed in a pull request like any other code. When you change which operator reviews, which command runs or where a person must decide, the change shows up as a diff.

  • Abudget sets the limits for the whole run.
  • BAn agent step names an operator and who receives the handoff.
  • CA command step is run by the engine, which compares the exit code.
  • DA gate step is a question for a person.

05Limits and the ledger

Every run has hard limits and leaves a log you can verify.

Each playbook carries three limits

minutes of wall-clock time maxMinutes
45
agent steps maxAgentSteps
6
handoffs from one operator to another maxHandoffs
4

These numbers are the budget of error-to-fix.

There is one global pause switch. While it is on, no new step starts, and each run carries on once the pause is lifted.

Every action goes into the ledger

Each entry is appended to a log and carries the hash of the entry before it. If someone edits an entry in the middle, the chain no longer matches, and you can check the chain yourself. The check catches accidents and careless edits. It does not stop a person who can write to the database file from rewriting the whole chain.

06Operators

Four operators ship with it, and each has one job.

They come as seed configuration, with a name, a role and written instructions for each one.

  1. Inspector

    @inspector

    Reproduces the error with the smallest failing case it can find, and says who is affected.

    It never edits source files.

  2. Fitter

    @fitter

    Writes the fix and a regression test as one focused change on a new branch.

    It writes the failing test before the fix.

  3. Checker

    @checker

    Reviews the diff in a fresh session, with no memory of how it was produced.

    It never reviews a change it wrote.

  4. Dispatcher

    @dispatcher

    Ships the change, watches the rollout and reports the error rate and latency before and after.

    It acts only after a person has approved.

Memory goes through Ruflo. Each operator’s memory is kept in Ruflo when it is running, and in a local store when it is not.

07Where the line ends

What Switchyard does not do.

Switchyard is a new project, so read this list before you plan any work around it.

  • It is not a hosted service. You run it yourself.
  • It gives agents no cloud computers. They work on your machine.
  • No Slack or chat integration.
  • No mobile app.
  • No marketplace.
  • No multi-user accounts yet.

Live mode is early and unproven. It is the mode in which operators work in a real repository checkout and command steps really run. Agent sessions and test commands then run with your account's privileges and are not sandboxed, so point it only at repositories and signal sources you trust.

08Run it

It runs as one Node process with a SQLite file.

Everything stays on your machine. It sends no telemetry and loads no third-party fonts or scripts.

Open the console 

npm install
npm run build
npm start

Then open http://127.0.0.1:4310/app/ for the console. It needs Node 22.13 or later.

It starts in simulate mode, with scripted agents and dry-run commands. Watch a run end to end, then point it at a real repository.
